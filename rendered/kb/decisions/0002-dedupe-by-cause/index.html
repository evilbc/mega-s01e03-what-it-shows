The original ticket contains two known mechanisms. The cause table describes the old ticket system: its warning that the hint problem has no ticket refers to that export. The two linked GitHub tickets below track this investigation.

Shared parser reads month first

The shared parser treats date input as month first even when the tenant writes day first. For a day-first tenant, entering 07/04/2026 for 7 April produces 4 July. R-41200 and its correction R-41201 show this reversal. They are separate report IDs, so both count. R-41205 is another example: its French tenant uses day-first dates even though intake recorded an American browser locale and tagged it hint.

Fix parsing against the tenant’s explicit date convention, or accept an unambiguous format. Preserve month-first behavior for month-first tenants. Cover app, email, and the older booking form; a change to the newer form’s hint cannot fix those paths. Do not silently guess when a tenant is unknown.

The parser ticket and its exact report membership are in GitHub issue #2. Its count includes the unresolved timing reports listed below. That is the export’s classification, not proof that the parser caused every body in the group.

New booking form gives a month-first hint to day-first tenants

For booking-v3, the date field prints MM/DD/YYYY. A day-first tenant’s form interprets the input using the tenant’s convention. Following the printed hint can therefore reverse the date. R-41230, R-41241, and R-41251 come through this form at Copper Studio, Alder Physio, and Pale Harbour respectively.

For example, on Alder Physio’s de-DE form, a person following the hint types 04/07/2026 for 7 April. A day-first form reads that as 4 July. The expected behavior is a hint that matches the actual parser and the tenant locale.

Fix the displayed hint and validate its agreement with form parsing. This is a separate change from the shared parser fix. Track it in GitHub issue #1. Other channels at these same tenants can still belong to the parser issue.

Proposed triage decision

Deduplicate reports only when the evidence supports the same underlying problem in the same product and affected behavior. Record the tenant, its locale, form version, channel, expected date, observed date, and any reproducible trigger. Read the report body. Use the subject to find candidates, never to decide a merge. Use browser locale and intake tags as clues, never as the final classification.

The same subject can hide different causes, and different subjects can describe the same cause. Unknown tenants and unexplained behavior stay separate for investigation rather than being merged by default.
